# 03 · 记忆摘要：长期事实怎么进窗口

## 当时我怎么看这个问题

多会话产品里，用户会说「还是上次那个地址」。若每次只带本轮对话，模型必然失忆；若把所有历史原文灌进窗口，预算瞬间爆。需要一层 **memory**：把长期事实压成短摘要，以中等优先级进 packer。

我早期把「向量检索历史聊天」当成记忆——取回来的经常是寒暄与情绪句，真正的地址反而排后面。那是检索，不是记忆。

## 试过什么

1. **向量检索历史聊天**：相关，但易取出闲聊噪声；也难处理「地址已变更」的冲突。
2. **每次会话结束用大模型写记忆**：质量好，lab 难离线跑，且要处理冲突合并与提示注入攻击（用户试图改写系统记忆）。
3. **手工 key-value 档案**：可控，但要设计写入规则与展示格式。
4. **把记忆当普通 history 追加**：优先级不够，一挤就被丢掉。

## 为什么否决

否决「全文历史当记忆」。否决「记忆无结构」。本仓用**规则型记忆抽取**做可测最小闭环：从对话里抓「地址/姓名/偏好」等模式，合并进 `MemoryStore`，再 `to_pack_item()` 交给 packer。真生产可换成 LLM 摘要，**接口保持不变**。

## 最终怎么解

- `memory.py`：`MemoryStore.ingest_turn` / `summary_text` / `to_pack_item(priority=80)`
- 冲突策略：同 key 新值覆盖，并留 `updated_at`
- `cli pack`：演示「有历史 + 有记忆 + 有检索」的打包
- 单测：写入偏好后摘要必含关键词；打包结果能带上 memory

记忆的优先级要介于 pin 与普通 history 之间：太低会被闲聊挤掉，太高可能压过当前用户问题（本 demo 里当前问题也给了高优先级，可按产品调）。

## 用到的具体 skill / 技巧清单

| Skill | 用法 |
|-------|------|
| **结构化记忆槽** | address / preference / profile |
| **冲突覆盖策略** | 同 key 新值覆盖 + updated_at |
| **记忆→PackItem** | 统一进 packer |
| **离线可测** | 无 API |
| **优先级介于 pin 与 history** | 示例 80 |
| **与 budget 协同** | 记忆过长同样会被量token，需限制槽位数 |

## 代码解析（按文件路径）

### `lab/src/context_lab/memory.py`

正则抽取 demo 级事实；`summary_text` 拼成一段中文短记忆。扩展时优先加槽位，而不是把原文会话塞回去。

### `lab/src/context_lab/cli.py` + `lab/tests/test_packer.py`

`pack` 打印记忆摘要与最终 messages；测试保证 `ingest_turn` 后关键字段存在。

Context engineering 的本质不是「更多 token」，而是**在预算内保住正确的那一小撮约束与事实**——记忆层解决「跨会话」这一维，packer 解决「本请求塞不下」这一维。
